# 文档维护与改动验收

## 玩家操作流程验收

今后的玩家功能测试从玩家实际使用的入口开始。可以用脚本向游戏窗口发送鼠标、键盘或手柄输入。由正式界面决定哪个控件收到输入，再由游戏完成选择、切换、保存或同步。验收终点是玩家能观察到的结果。例如，选人后查看阵容是否增加，翻页后查看页码和名单是否变化。检查保存时从正常入口重新打开，检查队友是否收到结果时在接收方界面观察。

预期结果只用于比较。测试可以按场景要求点击某名选手，随后读取名单与预期比较。若直接把这名选手写入阵容再读取，选人的功能就没有经过测试。同理，禁止替程序选好待验证的父窗口或目标、直接触发按钮回调、写入待验证的保存或同步结果，再把这些值当作通过条件。

每条验收记录写明起始状态、实际操作、预期结果和独立观察到的界面响应。入口前可以准备已有存档等起始资料，记录中注明来源。单人和多人共用功能时，分别走实际有差异的入口，共用流程避免重复穷举。若流程止于建房入口，就记录到达建房入口；单步调用、协议返回、截图和编译成功都不能单独充当玩家流程通过的记录。

## 章节职责

对决战报从排位匹配、日程中的镜面约战和建筑师的实战选项分别验收。排位结束后核对同一窗口的积分与战况，切换牌序和牌面，再返回一次、重看上场。约战核对邀请对象、确认后的模式、结算与积分；建筑师核对前进、原版对话、正式赛结算与重赛。升级游戏时核对战斗历史的卡牌开始与完成条目、牌面、伤害与格挡、选牌事件、楼层历史 Variables 的保存与恢复，以及内置求解器的重复动作识别入口。

README 是目录与当前实现的查询入口；MODULES 负责模块边界；DATA_CONTRACTS 负责数据与编号；AI_FLOWS、PERSISTENCE_AND_COOP、GAME_AND_UI 负责各自完整流程；SOURCE_MAP / Source 负责静态双向依赖。性能与验收原始证据保留在维护者本地的 PERFORMANCE 及对应资料中。

开发文档仅记录真实实现、架构、接口、依赖和实测证据，供后续开发查询。方案及未实施设计只在对话中提交审阅，不写入本目录；已经批准但尚未实现的设计也不写入当前流程。

新的业务模块放入职责明确的章节，规模需要时拆为独立专题并从目录链接。已存在功能直接修改原章节，删除过时叙述。版本历史与当前规则分开，避免读者要拼接多次追加记录才能得到现状。

发布与本地安装前同步核对 NationalSpire.json.version 和 Diagnostics.ModVersion，并读取最终 DLL 元数据中的 ModVersion 常量确认构建结果。安装后核对目标目录的清单版本及 DLL、清单 SHA-256。Diagnostics.ModVersion 同时用于 CareerScreen 品牌版本、Entry 加载记录、诊断导出和 CoopRuntime.Compatibility 发布版本标识；修改常量后重新编译整个生产项目，使这些调用者使用同一版本。上述检查在构建与安装阶段执行。

每次更新 GitHub 时，必须同步更新根目录 README.md 中的已完成清单，记录本次实际完成的功能、修复与优化。发布验收须核对远程 README.md 中的本次完成条目。

## 游戏与求解器更新检查表

核对[出牌者阵营、紧勒和湮灭](GAME_AND_UI.md#出牌者阵营紧勒和湮灭)时，检查蜃景计算委托是否仍从卡牌参数读取名单、超能光束动画的目标、紧勒追加失血的伤害签名，血肉戏法接收负面状态实际变更的回调，以及内置求解器 AfterCardPlayedMirrors 和 ResolvePowerAmountChanges 的对应处理方法。在 0.113.1 的隔离客户端使用 LeaguePreview 的 LEAGUE_CARD_SIDES 残局可依次核对实际出牌、状态和动画目标，并检查同一盘面的一步求解结果。

**先确定更新的是哪一层。** 游戏更新时，核对游戏接口和牌效，并核对下表中相应的求解器实现；只升级内置求解器时，从打包、加载开始，核对局面复制、出牌、选牌和结束回合。若某张牌只改了触发时机，游戏和模组仍可能编译通过，此时要比较这张牌在推演和实战中各触发了几次、作用于谁、何时生效。

当前维护基线为国运尖塔 1.1.5。单人和多人开赛按实际方法签名选择处理方式。镜面对决另有独立判断：[LeagueSolverLink.Supported](../LeagueSolverLink.cs) 检查游戏是否提供愚者箭槽类型和 RunState.RunModels 属性。0.107.1 保留开包、收藏、交易、组卡和建筑师原对话，镜面匹配与建筑师对决入口不可选；0.113.0 提供对决。两个成员存在，只决定是否开放入口。新游戏即使通过这项判断，仍须核对下列战斗接口和牌效。玩家是否订阅独立求解器不参与判断。

### 求解器更新时从打包查到实战

升级内置求解器时，同时对照 LeagueForecast.Projection 的 ProjectRunRules 与上游 SimulatedCombatState 构造函数中接受的 RunModel 类型；核对 RunState.set_RunModels、ModHelper 的两种订阅者枚举、PredictionModHookSubscriberCapture.ValidateSubscriber、PredictionModPatchAudit.AuditCardOnPlay 的补丁和适配返回值，以及 PredictionCoverage.DescribeGap 的风险来源。卡牌审查与求解器补丁只安装在内置程序集；两处原版 ModHelper 枚举仅在临时战场与线程都匹配时才返回该战场的名单。

复核入口为 LeaguePreview/Sparring.Run。设置 LEAGUE_PROJECTION_HERO=plain、installed 或 mod，搭配 LEAGUE_WHITE_DUEL=1；第一种只启用陪练工具与国运尖塔，后两种加载同一套职业模组，第三种实际使用其中的模组职业。比较同种子的传奇黑暗蓄能机器人的 solver-review.txt 和 fight.jsonl：核对球的激发值、每次搜索返回的整段牌序、游戏实际出牌及逐击伤害，并分别统计首次推演、后续推演与备用选牌次数。测试输出只在指定隔离目录时启用。

### 怎样执行并留下结果

1. 记录目标游戏分支和版本、游戏程序集与模组 DLL 的 SHA-256、内置求解器及辅助库版本。在维护工作区用同一份发布 DLL，对每个受支持分支的实际 `sts2.dll` 执行 `NationalSpire.CompatibilityTests`。该工具的 README 提供命令。它检查主 DLL 的成员签名、类型加载及部分原生调用；内嵌求解器的运行时绑定、补丁插入位置、场景资源和音乐需按上表另查。
2. 改动游戏方法时，同时查正常调用、按名称查找的成员、异步方法内部和事件订阅。由[源码索引](SOURCE_MAP.md)找到调用者，再核对 [LiveCompatibility](../LiveCompatibility.cs)、LeagueNativeMatch.Install、FinalEndHooks.Install 及 LeagueForecast.Prepare 等实际安装位置。上游卡效即使保留原签名，也要查伤害来源、目标和回调顺序是否改变。
3. 选择和变更相关的真实玩家流程。维护工作区的 `NationalSpire.MultiplayerTests/LeaguePreview` 提供 Sparring、FinalTeamReview 和 Run-Sparring.ps1。已有定向入口包括 `LEAGUE_NATIVE_DOOM`、`LEAGUE_OWN_TURN_LOSS`、`LEAGUE_DECISION_CASE`、`LEAGUE_ARCHITECT`，以及配合建筑师场地检查的 `LEAGUE_ARCHITECT_AUDIO`。核对正式灾厄数值时启用 `LEAGUE_SHIPPING=1`，避免使用实验换算。记录实际游戏版本、输入局面、预期与实得结果，并分列静态检查、单人实机、本机双客户端和未验证范围。
4. 以后新增或改动游戏补丁、反射成员、场景节点、求解器接口或双方共用的战斗规则，在同一次修改中更新本表相应行、详细流程和函数索引。新增接入点归入具体玩家入口或求解器步骤；移除接入点时同步删除旧说明。

## 开始修改前

1. 阅读目录、负责章节及函数索引，核对源码摘要与当前文件。
2. 从改动函数向上查调用者、信号、委托和游戏补丁入口；向下查返回值、字段、磁盘、网络与界面消费者。
3. 明确哪些值是复制、引用、最新读取、请求快照、历史事实、实时显示或正式结果。
4. 说明具体行为变化、默认处理、限制及单人/多人/旧档范围，提交用户审阅。
5. 从完整操作列出各计算步骤、次数、数据规模、保存和同步节点，确定性能基线与目标。

这一步形成可审阅方案，不修改实现或测试代码。检查中发现需要改设计，重新说明完整方案与行为变化，等待审阅。
所有修改均须在实施前逐项说明当前行为、具体修改位置、采用的方法、执行顺序、默认处理、适用条件和受影响的流程，并取得用户审阅通过。要求适用于所有功能、代码、配置、数据、界面、存储、网络和发布操作；每次讨论中的具体例子只用于解释本次任务，不能缩小这条通用要求的适用范围。

验收须逐项对应已批准的方案，写明实际执行的操作、输入来源、执行环境、经过的组件、输出与副作用、验证结果和未验证项。真实运行、模拟响应、原始返回重放、静态检查和推断结论分别标明，不能互相替代；修改后的实现须有对应验证，不能把修改前的结果写成修改后的实测结果。

## 提示词合并与回归核对

提示词规则集中维护在所属共用协议、模板或工具说明中。任何模式均禁止通过附加系统消息加入或重复规则；消息结构的调整须单独审阅。活动意愿规则来自 ChatTools.ActivityIntentGuidance，只在工具的 send_message 总说明接入一次。文字邀约与附件区分、教学方向和普通交流定义均限于工具说明；普通活动与学习协议保持原文。核对完整请求中的接入次数、模式范围、原消息结构、实际活动交互与保存结果。提示词修改向用户逐字列出修改前后原文，保留玩家已确认的措辞。

玩家累计正式战绩和历届荣誉统一由 PrivatePublicContext.PlayerCompetitionRecord 组织，核对私聊、约会、群聊、自动新闻、评论与随机事件的全部调用关系；总场数包含平局，荣誉保留全部已取得赛季并遵循日期及个人／合作队伍归属。约会结束的 ToolEnding、示例和字段说明同时要求日记，重新生成更新同一条目。工具的 TeachingGuidance 区分玩家与NPC，NPC接受教学并形成实际学习变化时才登记学习；普通学习协议保持原文。群聊已有活动使用 PrivateInteractionIds.Resolve 解析短编号后再读取所属记录。

审查涉及模型输出的 PR 时，同时比较可编辑模板、程序固定指令、请求资料、消息顺序、目标识别与合法性检查、解析、预览、效果执行、保存及旧模板转换。作者说明与实际源码行为分别核对，沿输入到保存的完整调用流程确认影响；效果解析代码保持原样，也可能通过提示词或目标检查改变输出及结算。对照当前本地源码与已确认的模型实测记录；PR 能编译或文本冲突已经解决，只能说明相应检查通过。前缀和参与者选择功能与效果目标、效果描述、格式、提示词等改动分别列明审阅范围。当前随机事件的完整流程与实测范围见 [AI_FLOWS.md](AI_FLOWS.md#随机事件流程)，源码入口为 RandomEventPrompts.Compose、PromptLibrary.Get/EditableText、RandomEventParser、RandomEventEffects 及 PrivatePublicContext。以下是当前实现中已经形成的核对项目。

## 索引的维护

每个 Source 文档记录源码 SHA-256，函数保留签名、输入默认值、返回类型、调用者、调用与字段引用。模块移动、函数签名和调用变化时，同时更新双向文件关系与相关函数条目。类拆成 partial 后仍按源码文件定位。

生成索引使用 Roslyn 语义绑定，不通过函数同名匹配猜测目标。分析范围包括类型、字段初始化、参数、返回类型、方法组、函数调用及属性引用。nameof 是编译期名称表达式，不计函数执行。局部函数以所在声明位置区分；匿名函数计入所属函数。自动索引是查找入口，不代替流程说明。

索引使用 Roslyn 语义绑定生成，方法记录保留在维护者本地的 INDEX_GENERATION.md。生成过程只输出 Markdown 文档，不编译生产模组、不执行游戏。新增隐式构造函数、接口动态派发、委托目标、运行时反射和游戏补丁须在流程中明确，不把“没有直接调用者”理解为没有使用者。

修改前后检查：源码摘要匹配；函数与文件链接有效；调用者与被调用者两侧一致；负责章节没有互相冲突；不存在“方案”混写为“现有实现”。

## 性能验证与正确性验收

每项新功能或修改都执行与实际影响范围匹配的性能测试。架构阶段先识别次数随资料规模或成员数增长的地方，避免先引入逐人全量复制、逐字重建、重复序列化，再把更改成本留给后续修复。

纯数值、文案等影响明确、效果直观的小改动，仅执行必要的编译、针对性检查和性能确认，不重复全量复杂回归。涉及保存、同步、解析、数据结构或流程变化时，再扩大验证。已有可复用测试继续保留，调整数值时同步维护相应预期。

性能优化必须分别证明：输入选择未变；输出和保存状态符合批准范围；同步可见性与顺序未变；原恢复机制仍能处理失败或中断；整体耗时满足目标。解释意图与静态代码检查不代替这些证据。

纯性能项比较完整上下文、候选顺序、随机状态、解析结果、业务变化、保存字段和每人广播权限。含明确业务修改时，只允许出现已批准差异，单列其余等价检查。

所有量化结论注明构建、源码摘要、数据规模、环境、测量边界、样本次数、逐次/最大值和未测部分。出现新的超过目标步骤，要记入完整流程，不能从报表移除。

## 日志增长与诊断完整性验收

本模组全部自动日志遵守工作区 AGENTS.md 的日志增长与诊断完整性规则。适用对象包括普通运行、模型请求与返回、解析与交互检查、比赛、保存恢复、多人收发、错误及性能记录，同时检查内存队列、缓存、临时文件和未完成传输。玩家主动导出的诊断 ZIP 由玩家管理。

自动记录归入 LogRouting 的固定功能组，各组独立保留最近五份，共用 LogStorage 轮换与读取。人物、会话、事件及尝试编号进入记录正文。长错误统一经 Diagnostics.RetainErrors 归档，存档摘要与界面共用 ErrorTextLimit；完整错误读取和导出沿同一功能文件组处理。具体文件与保留边界见 DATA_CONTRACTS，后续入口复用现有归属和公共入口。

修改前从磁盘写入和内存累积入口核对全部来源，再向上检查调用者、向下检查轮换、读取、导出和多人收集。逐项说明增长约束、保留范围、轮换条件、完整记录及操作关联；数值依据实际规模和保留需求提交审阅。所有自动日志复用统一的日志管理入口。

诊断内容须对应具体生涯、事件或对局、生成或重试次数、阶段和时间，并包含排查所需的实际输入、原始返回、解析或判定结果与错误。保存恢复须记录入口条件、跳过原因、完成结果和实际检查点。导出及多人收集完整覆盖已批准保留范围，传输总量限制不得截断或拒收诊断内容；失败或缺失须明确列出。

日志及传输修改须保证游戏、记录和导出继续正常执行。容量、长度和人为防御条件不得触发强制截断、报错或失败；临时写入及传输异常在后台静默处理，保留完整资料并恢复未完成操作。处理状态和真实错误写入诊断记录，界面与游戏操作继续运行。具体恢复行为须在实施前说明并经用户批准。

验收同时核对长期连续写入、不断创建新文件、单条大记录、重复错误、重新生成、生成及解析失败、退出重启、切换生涯、旧记录兼容和完整导出。涉及多人时验证客机收集、传输中断及重连。记录磁盘占用、文件数量、内存与耗时，比较原始输入和最终导出内容，列出实际覆盖范围、保留边界和未验证条件。本节为维护与验收要求，当前各入口的实现仍以负责章节和源码为准。

当前实现由 LogStorage 统一管理私聊与约会、群聊、社区、周刊、随机事件、比赛、保存与多人同步、其他运行八个固定功能文件组，每组当前加四份历史，完整记录写入后在下一条之前轮换；固定性能文件覆盖写入。写入句柄按固定功能复用，每条刷新，首次打开及轮换后整理历史文件；清理失败在后续写入继续处理。新增日志必须复用该入口，并检查对应内存容器、导出、多人收集和退出释放。保留范围外的较早记录随轮换到期；导出时完整读取保留范围。写入暂不可用的队列范围、重试及统计见 DATA_CONTRACTS。开局观察继续使用比赛组，逐帧资源处理和非开局回调开销见 GAME_AND_UI。容量审计、逐项压力测试与性能原始资料位于维护者本地 LOG_DIAGNOSTIC_VERIFICATION.md；该原始验收文件不随公开架构文档发布。
