# 文档维护与改动验收

## 章节职责

README 是目录与当前实现的查询入口；MODULES 负责模块边界；DATA_CONTRACTS 负责数据与编号；AI_FLOWS、PERSISTENCE_AND_COOP、GAME_AND_UI 负责各自完整流程；SOURCE_MAP / Source 负责静态双向依赖。性能与验收原始证据保留在维护者本地的 PERFORMANCE 及对应资料中。

开发文档仅记录真实实现、架构、接口、依赖和实测证据，供后续开发查询。方案及未实施设计只在对话中提交审阅，不写入本目录；已经批准但尚未实现的设计也不写入当前流程。

新的业务模块放入职责明确的章节，规模需要时拆为独立专题并从目录链接。已存在功能直接修改原章节，删除过时叙述。版本历史与当前规则分开，避免读者要拼接多次追加记录才能得到现状。

## 开始修改前

1. 阅读目录、负责章节及函数索引，核对源码摘要与当前文件。
2. 从改动函数向上查调用者、信号、委托和游戏补丁入口；向下查返回值、字段、磁盘、网络与界面消费者。
3. 明确哪些值是复制、引用、最新读取、请求快照、历史事实、实时显示或正式结果。
4. 说明具体行为变化、默认处理、限制及单人/多人/旧档范围，提交用户审阅。
5. 从完整操作列出各计算步骤、次数、数据规模、保存和同步节点，确定性能基线与目标。

这一步形成可审阅方案，不修改实现或测试代码。检查中发现需要改设计，重新说明完整方案与行为变化，等待审阅。

## 每项变更必须填写的内容

以下内容写入该功能的负责章节，取代原实现说明，不复制成一份尾部更新日志。

| 项目 | 要说明的问题 |
| --- | --- |
| 实现目的 | 已实现的行为解决什么问题；适用范围和现有边界是什么 |
| 输入 | 由哪个函数/字段/事件提供；数据什么时候形成；是否可能在等待期间变化 |
| 调用 | 准确函数名、调用条件、顺序；委托/事件/反射目标；重复执行条件 |
| 输出 | 返回值与修改字段；谁继续使用；是否还会进入帖子、记忆、总结或下一轮 |
| 数据归属 | 单人实例、房主最新数据、个人视图、客户端、本机配置各自负责什么 |
| 保存 | 每次保存含什么变化；谁依赖保存后状态；原版文件是否参与 |
| 同步 | 完整快照和流式字段；接收权限、版本、顺序、检查点、界面刷新 |
| 失败与离开 | 原有取消、失败、重试和恢复；请求期间跨天、开赛、切换或退出怎样处理 |
| 兼容 | 旧字段缺失、旧模板、历史记录、身份变化、已有进行中对局怎样处理 |
| 性能 | 全部计算阶段、次数、各次/最大耗时、累计与总耗时、分配及线程影响 |
| 验证 | 同输入基线、优化后差异、业务副作用、文件/网络/界面、极端中断、真实或替身环境 |
| 缺口 | 尚未验证的具体入口与运行条件；不使用模糊的“已全面验证” |

## 索引的维护

每个 Source 文档记录源码 SHA-256，函数保留签名、输入默认值、返回类型、调用者、调用与字段引用。模块移动、函数签名和调用变化时，同时更新双向文件关系与相关函数条目。类拆成 partial 后仍按源码文件定位。

生成索引使用 Roslyn 语义绑定，不通过函数同名匹配猜测目标。分析范围包括类型、字段初始化、参数、返回类型、方法组、函数调用及属性引用。nameof 是编译期名称表达式，不计函数执行。局部函数以所在声明位置区分；匿名函数计入所属函数。自动索引是查找入口，不代替流程说明。

索引使用 Roslyn 语义绑定生成，方法记录保留在维护者本地的 INDEX_GENERATION.md。生成过程只输出 Markdown 文档，不编译生产模组、不执行游戏。新增隐式构造函数、接口动态派发、委托目标、运行时反射和游戏补丁须在流程中明确，不把“没有直接调用者”理解为没有使用者。

修改前后检查：源码摘要匹配；函数与文件链接有效；调用者与被调用者两侧一致；负责章节没有互相冲突；不存在“方案”混写为“现有实现”。

## 性能验证与正确性验收

每项新功能或修改都执行与实际影响范围匹配的性能测试。架构阶段先识别次数随资料规模或成员数增长的地方，避免先引入逐人全量复制、逐字重建、重复序列化，再把更改成本留给后续修复。

纯数值、文案等影响明确、效果直观的小改动，仅执行必要的编译、针对性检查和性能确认，不重复全量复杂回归。涉及保存、同步、解析、数据结构或流程变化时，再扩大验证。已有可复用测试继续保留，调整数值时同步维护相应预期。

性能优化必须分别证明：输入选择未变；输出和保存状态符合批准范围；同步可见性与顺序未变；原恢复机制仍能处理失败或中断；整体耗时满足目标。解释意图与静态代码检查不代替这些证据。

纯性能项比较完整上下文、候选顺序、随机状态、解析结果、业务变化、保存字段和每人广播权限。含明确业务修改时，只允许出现已批准差异，单列其余等价检查。

所有量化结论注明构建、源码摘要、数据规模、环境、测量边界、样本次数、逐次/最大值和未测部分。出现新的超过目标步骤，要记入完整流程，不能从报表移除。

## 完成与长期维护

完成报告链接当前章节与实测证据。没有执行真实模型、真实网络、游戏或故障中断，就明确写未执行。没有达到目标，就记录未达到，不用其他场景的改善代替。

文档维护与功能修改是同一项工作的组成部分。会话摘要保留目录位置、已批准范围、当前实现、未完成验证；后续先读文档和源码再继续。当前章节需要表达可以直接查到的事实，不能把用户此前纠正当作唯一记忆来源。

Development 中已获授权的架构、接口、维护规则与源码依赖索引可以公开，具体文件以 .gitignore 逐项放行的路径为准。内部审阅、未实施方案、性能验收原始资料、索引生成工具、玩家存档及凭据不公开，不强制加入 Git。

PR 必须同步修改受影响的流程章节、数据约定和函数条目，更新双向调用关系及源码摘要；不能仅在文档末尾增加版本记录。实现相同规则的各入口必须复用同一负责模块，具体要求见[贡献说明](../CONTRIBUTING.md#模块复用与长期维护)。
